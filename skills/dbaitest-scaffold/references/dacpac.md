# SQL Server database projects (.dacpac)

A database project (SSDT, or the SDK-style `Microsoft.Build.Sql`) keeps one object per file,
and objects depend on each other across folders in both directions, so no file order applies
them. `DbAiTest.MsSql.Dacpac` deploys the built `.dacpac` with DacFx, in dependency order.

Which flag:

- **SDK-style project** (`<Project Sdk="Microsoft.Build.Sql">`, or `MSBuild.Sdk.SqlProj`):
  `--sqlproj`. `dotnet test` builds the dacpac.
- **Classic Visual Studio SSDT project** (imports `Microsoft.Data.Tools.Schema.SqlTasks.targets`):
  the `dotnet` CLI cannot build it. Build it in Visual Studio or with MSBuild and use `--dacpac`
  with the output (`bin/<Configuration>/<Name>.dacpac`). The generator refuses a classic project
  given to `--sqlproj`.

## Wiring (generated by `--schema dacpac`)

- `--sqlproj`: a `ProjectReference` to the `.sqlproj` with `ReferenceOutputAssembly="false"`,
  so `dotnet test` builds the dacpac first, and a `CopyDacpacs` target that copies **every**
  `.dacpac` from the project's output next to the test binaries. Referenced dacpacs
  (`master.dacpac` from `Microsoft.SqlServer.Dacpacs.Master`, another project's) are resolved
  from the folder the dacpac is deployed from, so they must travel with it.
- `--dacpac`: a `None` item that copies the prebuilt dacpac and its neighbours to the output.
- The test class overrides `SchemaSource`:

  ```csharp
  protected override SchemaSource? SchemaSource =>
      new DacpacSchemaSource(Path.Join(AppContext.BaseDirectory, "Shop.Database.dacpac"));
  ```

  Use `Path.Join(AppContext.BaseDirectory, ...)`: a relative path in a schema source resolves
  against the current directory, not the test binaries. Do not combine `SchemaSource` with
  `SchemaRoot` or `SchemaLoadOptions`; that throws.

## Deploy options

Without options: nothing is dropped, possible data loss does not block the deploy,
database-level settings are skipped, and every command has the engine's timeout. To set SQLCMD
variables, start from the defaults (a bare `new DacDeployOptions()` has no timeout at all):

```csharp
protected override SchemaSource? SchemaSource
{
    get
    {
        var options = DacpacSchemaSource.CreateDefaultOptions(new MsSqlEngine());
        options.SqlCommandVariableValues["Environment"] = "Test";
        return new DacpacSchemaSource(Path.Join(AppContext.BaseDirectory, "Shop.Database.dacpac"), options);
    }
}
```

Classes whose dacpac or options differ get separate containers.

## Reference data from a post-deployment script

`CleanAsync` empties every table, including rows the post-deployment script seeded. Copy the
script to the output and run it again after cleaning. `Harness.ExecuteAsync` sends the text as
one command, so the script must be idempotent and contain no `GO`, `:r` or `:setvar`:

```xml
<None Include="..\Shop.Database\Script.PostDeployment.sql" Link="Script.PostDeployment.sql" CopyToOutputDirectory="PreserveNewest" />
```

```csharp
[TestInitialize]
public async Task ResetAsync()
{
    await Harness.CleanAsync(TestContext.CancellationToken);
    var script = await File.ReadAllTextAsync(
        Path.Join(AppContext.BaseDirectory, "Script.PostDeployment.sql"), TestContext.CancellationToken);
    await Harness.ExecuteAsync(script, TestContext.CancellationToken);
}
```

## Good to know

- A missing dacpac fails before any container starts, with the full path it looked for.
- The dacpac file name is the database project's file name (`Shop.Database.sqlproj` →
  `Shop.Database.dacpac`). If the project sets `<SqlTargetName>` (or `<TargetName>`), change the
  name in `DatabaseTests.cs` to match.
- Pin the SDK: put the `Microsoft.Build.Sql` version in `global.json` under `msbuild-sdks` and
  write `<Project Sdk="Microsoft.Build.Sql">` without a version.
- DacFx sends usage telemetry unless `DACFX_TELEMETRY_OPTOUT=1`; set
  `<DacFxTelemetryEnabled>false</DacFxTelemetryEnabled>` in the `.sqlproj` for build time.
